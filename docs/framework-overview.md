# Performance Framework Overview

## System Architecture

This performance management system is built on three pillars:

1. **Universal Criteria**: Standards that apply to all engineering roles
2. **Role-Specific Competencies**: Skills and behaviors unique to each role/level
3. **Clear Scoring**: Transparent 1-4 scale with actionable definitions

## Design Principles

### Enable, Don't Constrain

Traditional performance systems often:
- Force a bell curve distribution
- Create competition between team members
- Obscure criteria behind subjective judgments

This system instead:
- Allows everyone to achieve top ratings
- Creates shared standards for success
- Documents clear, measurable criteria

### Evolving Competencies

Competencies aren't static—they evolve as you progress:

| Level | Focus |
|-------|-------|
| Junior (IC1) | Learning, executing defined tasks, asking questions |
| Mid (IC2) | Independence, owning features, quality consistency |
| Senior (IC3) | Technical leadership, mentoring, system thinking |
| Staff (IC4) | Cross-team impact, architecture, strategic thinking |
| Principal (IC5) | Org-wide influence, innovation, technical vision |

Some competencies only appear at higher levels (e.g., "Mentoring" starts at Senior).

### Two-Part Evaluation

Every role evaluation consists of:

**Part 1: Universal Criteria (Same for Everyone)**
- Craft/Quality
- Speed
- Adaptiveness

**Part 2: Role-Specific Competencies (2-4 per role/level)**
- Unique to role function
- Increase in scope/complexity with level
- Reflect what "good" looks like at each level

## Universal Criteria Explained

### Craft/Quality

**What it means**: Excellence in your core role responsibilities

For a Software Engineer: Clean, tested, maintainable code
For a Data Engineer: Reliable, efficient data pipelines
For an EM: Effective team management and delivery

**Level 4 looks like**:
- Consistently high-quality output
- Attention to edge cases and error handling
- Code/work that others can easily understand and maintain
- Proactive about quality (doesn't wait for review feedback)

### Speed

**What it means**: Reasonable execution pace + proactive unblocking

This is NOT about working fast or long hours. It's about:
- Working at an appropriate pace for the complexity
- Not letting blockers fester
- Asking for help when stuck

**Level 4 looks like**:
- "I'm stuck on X. I've tried A and B. Can I get your input?"
- Raises blockers before they become critical
- Delivers within reasonable timeframes
- Communicates early if timelines are at risk

**Level 3 looks like**:
- "I was stuck for three days but didn't want to bother anyone"
- Good work but unnecessary delays
- Waiting to be rescued instead of asking for help

### Adaptiveness

**What it means**: Willingness to change and flexibility

**Level 4 looks like**:
- Embraces feedback and iterates
- Adjusts approach based on new information
- Flexible when priorities shift
- Open to different ways of solving problems

**Level 3 looks like**:
- Resistant to changing approaches
- "That's not how we did it at my last company"
- Struggles with ambiguity or pivots

## Role-Specific Competencies

### How They Work

Each role has 2-4 competencies specific to that function and level:

**Example: Software Engineer**

| Level | Competencies |
|-------|-------------|
| Junior (IC1) | Code Quality, Learning Agility |
| Mid (IC2) | Code Quality, Technical Problem Solving, Collaboration |
| Senior (IC3) | Code Quality, Technical Problem Solving, System Design, Mentoring |
| Staff (IC4) | Technical Leadership, Architecture, Cross-Team Collaboration, Strategic Thinking |

### Competency Progression

Competencies evolve in two ways:

1. **Same competency, higher bar**: "Code Quality" at IC3 expects more than at IC1
2. **New competencies appear**: "Mentoring" only starts at IC3

### Documentation Structure

Each competency has:
- **Definition**: What it means
- **Level 4 behaviors**: Observable behaviors that demonstrate excellence
- **Level 3 behaviors**: Where improvement is needed
- **Level 2/1 behaviors**: Unacceptable performance indicators
- **Development suggestions**: How to grow in this area

## Career Level Framework

### Individual Contributor Track

| Level | Title Pattern | Experience | Scope |
|-------|--------------|------------|-------|
| IC1 | Junior | 0-2 years | Task execution |
| IC2 | Mid-Level | 2-4 years | Feature ownership |
| IC3 | Senior | 4-7 years | Technical leadership |
| IC4 | Staff | 7-12 years | Cross-team impact |
| IC5 | Principal | 12+ years | Org-wide influence |

### Management Track

| Level | Title | Scope |
|-------|-------|-------|
| M1 | Engineering Manager | 4-8 direct reports |
| M2 | Senior EM | 8-12 reports or multiple teams |
| M3 | Director | Managing managers (20-40 engineers) |
| M4 | VP | Managing directors (40+ engineers) |

## Calibration Process

### Purpose

Ensure consistent application of standards across:
- Different managers
- Different teams
- Different offices/locations

### Process

1. **Manager Preparation**: Complete evaluations with evidence
2. **Calibration Session**: Managers present ratings to peer group
3. **Discussion**: Challenge assumptions, ensure consistency
4. **Finalization**: Adjust ratings if needed based on calibration

### Calibration Questions

- "Would this person get the same rating with a different manager?"
- "Is the evidence sufficient to support this rating?"
- "Are we applying the same standard as last cycle?"

## System Benefits

### For Employees
- Clear understanding of expectations
- Transparent path to top rating
- Actionable feedback for improvement
- Fair, consistent evaluation

### For Managers
- Objective criteria reduce bias
- Easier performance conversations
- Clear framework for feedback
- Defensible decisions

### For Organization
- Consistent talent evaluation
- Data-driven promotion decisions
- Reduced legal risk
- Culture of high performance
