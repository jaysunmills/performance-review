# Software Engineer Competency Rubric

This rubric defines the role-specific competencies for Software Engineers at each level. All engineers are also evaluated on the three [Universal Criteria](../../../docs/universal-criteria.md): Craft/Quality, Speed, and Adaptiveness.

---

## Level Overview

| Level | Title | Experience | Key Competencies |
|-------|-------|------------|------------------|
| IC1 | Junior Software Engineer | 0-2 years | Code Quality, Learning Agility |
| IC2 | Software Engineer | 2-4 years | Code Quality, Technical Problem Solving, Collaboration |
| IC3 | Senior Software Engineer | 4-7 years | Code Quality, Technical Problem Solving, System Design, Mentoring |
| IC4 | Staff Software Engineer | 7-12 years | Technical Leadership, Architecture, Cross-Team Collaboration, Strategic Thinking |
| IC5 | Principal Software Engineer | 12+ years | Technical Vision, Innovation, Organizational Impact, Industry Expertise |

---

## IC1: Junior Software Engineer

### Scope
Task execution within defined boundaries. Focus on learning and building foundational skills.

### Competencies

#### Code Quality

**Definition**: Writing clean, tested, maintainable code for simple features

**Level 4 - Meets Expectations:**
- Writes clean, readable code that follows team standards
- Includes appropriate tests for code changes
- Handles common edge cases and error conditions
- Code passes review with minor comments
- Commits are well-organized and documented

**Level 3 - Needs Improvement:**
- Code works but has style/readability issues
- Tests are incomplete or missing
- Misses some edge cases
- Requires multiple review rounds for same issues

**Level 2/1 - Below Expectations:**
- Code frequently broken or doesn't compile
- Ignores feedback from reviews
- No tests or documentation

**Development Suggestions:**
- Study team style guide and examples
- Pair program with senior engineers
- Review own code before submitting
- Practice writing tests first

#### Learning Agility

**Definition**: Ability to learn quickly and apply new knowledge effectively

**Level 4 - Meets Expectations:**
- Asks thoughtful questions
- Takes notes and doesn't ask the same question twice
- Seeks out learning resources proactively
- Applies feedback from reviews to future work
- Shows improvement over time

**Level 3 - Needs Improvement:**
- Asks questions but doesn't retain answers
- Waits to be taught instead of seeking information
- Slow to apply feedback
- Limited initiative in learning

**Level 2/1 - Below Expectations:**
- Doesn't ask questions when stuck
- Makes same mistakes repeatedly
- Resistant to learning new approaches

**Development Suggestions:**
- Keep an engineering journal
- Set weekly learning goals
- Request feedback proactively
- Find a mentor

## IC2: Software Engineer

### Scope
Feature ownership with some independence. Expected to deliver end-to-end with occasional guidance.

### Competencies

#### Code Quality

**Definition**: Consistently producing well-engineered features with thorough testing

**Level 4 - Meets Expectations:**
- Delivers complete, production-ready features
- Comprehensive test coverage including edge cases
- Code is performant and handles errors gracefully
- Proactively improves code quality beyond requirements
- Considers security and accessibility

**Level 3 - Needs Improvement:**
- Features work but have gaps in testing or error handling
- Performance not considered
- Needs frequent guidance on quality expectations

**Level 2/1 - Below Expectations:**
- Frequent bugs in production
- Doesn't learn from quality issues
- Impacts team velocity

**Development Suggestions:**
- Create personal quality checklist
- Study production incidents for patterns
- Practice performance testing
- Get early feedback on designs

#### Technical Problem Solving

**Definition**: Ability to debug issues and solve technical problems independently

**Level 4 - Meets Expectations:**
- Debugs and resolves issues systematically
- Uses appropriate tools and techniques
- Identifies root causes, not just symptoms
- Documents solutions for others
- Knows when to escalate vs. keep digging

**Level 3 - Needs Improvement:**
- Can solve problems but takes too long
- Doesn't document solutions
- Sometimes treats symptoms rather than causes

**Level 2/1 - Below Expectations:**
- Cannot debug without significant help
- Gets stuck and doesn't ask for help
- Applies random fixes hoping something works

**Development Suggestions:**
- Learn debugging tools deeply
- Practice reading stack traces
- Study system architecture
- Keep a debugging playbook

#### Collaboration

**Definition**: Working effectively with team members and stakeholders

**Level 4 - Meets Expectations:**
- Participates actively in code reviews (giving and receiving)
- Communicates clearly in written and verbal formats
- Helps teammates when asked
- Raises concerns and suggestions constructively
- Keeps stakeholders informed

**Level 3 - Needs Improvement:**
- Participates minimally in team activities
- Communication is unclear or inconsistent
- Works in isolation

**Level 2/1 - Below Expectations:**
- Dismissive in code reviews
- Poor communication causing issues
- Creates friction with teammates

**Development Suggestions:**
- Practice giving constructive feedback
- Write clearer commit messages and PRs
- Attend and participate in team meetings
- Pair with different team members

## IC3: Senior Software Engineer

### Scope
Technical leadership within the team. Expected to lead projects, mentor others, and improve team practices.

### Competencies

#### Code Quality

**Definition**: Setting and exemplifying code quality standards for the team

**Level 4 - Meets Expectations:**
- Code serves as example for team
- Identifies and pays down tech debt
- Improves team standards and practices
- Catches subtle issues in code reviews
- Considers long-term maintainability

**Level 3 - Needs Improvement:**
- Good personal code quality but doesn't raise team level
- Doesn't address tech debt
- Reviews are superficial

**Level 2/1 - Below Expectations:**
- Quality regression from IC2 level
- Negative impact on team standards

#### Technical Problem Solving

**Definition**: Solving complex problems and helping others develop problem-solving skills

**Level 4 - Meets Expectations:**
- Solves complex, ambiguous problems
- Teaches problem-solving approaches to others
- Anticipates problems before they occur
- Creates tools or docs that help team solve problems

**Level 3 - Needs Improvement:**
- Solves own problems but doesn't help others
- Doesn't anticipate issues
- Hoards knowledge

**Level 2/1 - Below Expectations:**
- Struggles with complex problems
- Cannot guide others

#### System Design

**Definition**: Designing and implementing complex features and systems

**Level 4 - Meets Expectations:**
- Designs features that are scalable, reliable, and maintainable
- Considers operational concerns (monitoring, debugging, deployment)
- Makes appropriate trade-offs and documents decisions
- Breaks down complex work for team
- Understands and improves overall system architecture

**Level 3 - Needs Improvement:**
- Designs work but miss important considerations
- Doesn't document decisions
- Over-engineers or under-engineers solutions

**Level 2/1 - Below Expectations:**
- Designs cause problems in production
- Cannot handle complexity at this level

**Development Suggestions:**
- Study system design patterns
- Review architecture of systems you use
- Practice designing systems in interviews/exercises
- Get design feedback before implementation

#### Mentoring

**Definition**: Developing junior team members through guidance and feedback

**Level 4 - Meets Expectations:**
- Actively mentors 1-2 junior engineers
- Provides regular, actionable feedback
- Helps mentees set and achieve goals
- Creates learning opportunities
- Adjusts approach based on mentee needs

**Level 3 - Needs Improvement:**
- Answers questions but doesn't proactively mentor
- Feedback is too harsh or too gentle
- Doesn't follow up on mentee progress

**Level 2/1 - Below Expectations:**
- Avoids or refuses mentoring
- Negative impact on mentees

**Development Suggestions:**
- Request to mentor someone
- Study effective feedback techniques
- Ask for feedback on your mentoring
- Learn coaching models (GROW, etc.)

## IC4: Staff Software Engineer

### Scope
Cross-team technical impact. Expected to drive architecture, influence multiple teams, and solve organization-level technical challenges.

### Competencies

#### Technical Leadership

**Definition**: Leading technical direction across multiple teams

**Level 4 - Meets Expectations:**
- Sets technical direction adopted by multiple teams
- Drives consensus on technical decisions
- Unblocks teams on difficult technical challenges
- Builds technical credibility across organization
- Balances technical ideals with business reality

**Level 3 - Needs Improvement:**
- Leads within own team but not across teams
- Struggles to build consensus
- Technical direction not adopted

**Level 2/1 - Below Expectations:**
- Unable to lead at this scope
- Creates technical silos

#### Architecture

**Definition**: Designing systems that span teams and major technical boundaries

**Level 4 - Meets Expectations:**
- Designs systems used across organization
- Makes build vs. buy decisions
- Evolves architecture incrementally
- Balances innovation with stability
- Creates architectural standards and patterns

**Level 3 - Needs Improvement:**
- Good designs but doesn't drive adoption
- Over-architects or doesn't consider constraints
- Doesn't document architectural decisions

**Level 2/1 - Below Expectations:**
- Architecture causes widespread problems
- Cannot operate at this scope

#### Cross-Team Collaboration

**Definition**: Working effectively across team boundaries to achieve shared goals

**Level 4 - Meets Expectations:**
- Builds relationships across teams
- Facilitates cross-team technical discussions
- Resolves cross-team conflicts
- Represents team's technical interests effectively
- Enables other teams to succeed

**Level 3 - Needs Improvement:**
- Works well with some teams but not others
- Doesn't proactively build relationships
- Own team focus over company focus

**Level 2/1 - Below Expectations:**
- Creates cross-team friction
- Territorial or siloed thinking

#### Strategic Thinking

**Definition**: Connecting technical work to business objectives

**Level 4 - Meets Expectations:**
- Understands company strategy and competitive landscape
- Proposes technical initiatives aligned with business goals
- Thinks 1-2 years ahead
- Identifies emerging technologies with business impact
- Makes trade-offs considering business context

**Level 3 - Needs Improvement:**
- Good technical thinking but disconnected from business
- Focuses only on near-term
- Doesn't consider business context in decisions

**Level 2/1 - Below Expectations:**
- Technical decisions misaligned with business
- Cannot think beyond immediate tasks

## IC5: Principal Software Engineer

### Scope
Organization-wide technical influence. Expected to define strategy, drive innovation, and solve the hardest problems.

### Competencies

#### Technical Vision

**Definition**: Defining long-term technical direction for the organization

**Level 4 - Meets Expectations:**
- Creates compelling technical vision
- Articulates 3-5 year technical roadmap
- Aligns technical strategy with business strategy
- Inspires others with technical vision
- Evolves vision based on feedback and changes

**Level 3 - Needs Improvement:**
- Has vision but cannot communicate or drive adoption
- Vision disconnected from reality
- Doesn't evolve thinking

**Level 2/1 - Below Expectations:**
- No clear technical vision
- Vision causes organizational problems

#### Innovation

**Definition**: Driving adoption of new technologies and approaches

**Level 4 - Meets Expectations:**
- Identifies and evaluates emerging technologies
- Leads proof-of-concepts for new approaches
- Drives adoption of valuable innovations
- Balances innovation with stability
- Creates innovation culture in teams

**Level 3 - Needs Improvement:**
- Innovates personally but doesn't spread it
- Chases shiny objects without business value
- Risk averse about new approaches

**Level 2/1 - Below Expectations:**
- No innovation or harmful innovation
- Blocks valuable new approaches

#### Organizational Impact

**Definition**: Improving engineering capabilities across the organization

**Level 4 - Meets Expectations:**
- Improves engineering productivity org-wide
- Creates systems/tools used across company
- Raises technical bar for entire organization
- Influences hiring and technical standards
- Develops other technical leaders

**Level 3 - Needs Improvement:**
- Impact limited to part of organization
- Doesn't develop others
- Personal contribution over organizational improvement

**Level 2/1 - Below Expectations:**
- No measurable organizational impact
- Negative impact on organization

#### Industry Expertise

**Definition**: Being a recognized expert and representing the company externally

**Level 4 - Meets Expectations:**
- Recognized expert in relevant domains
- Represents company at conferences/events
- Publishes influential technical content
- Builds relationships with peers at other companies
- Brings external perspectives into company

**Level 3 - Needs Improvement:**
- Expert internally but not known externally
- Doesn't engage with technical community
- Doesn't bring external perspectives

**Level 2/1 - Below Expectations:**
- Not recognized as expert
- Damages company reputation externally
