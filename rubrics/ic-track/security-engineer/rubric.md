# Security Engineer Competency Rubric

This rubric defines the role-specific competencies for Security Engineers at each level. All engineers are also evaluated on the three [Universal Criteria](../../../docs/universal-criteria.md): Craft/Quality, Speed, and Adaptiveness.

**Note**: Security Engineering typically requires prior experience, so this track starts at IC2.

---

## Level Overview

| Level | Title | Experience | Key Competencies |
|-------|-------|------------|------------------|
| IC2 | Security Engineer | 2-4 years | Security Implementation, Threat Awareness, Collaboration |
| IC3 | Senior Security Engineer | 4-7 years | Security Implementation, Security Architecture, Threat Modeling, Mentoring |
| IC4 | Staff Security Engineer | 7-12 years | Technical Leadership, Security Architecture, Cross-Team Collaboration, Strategic Thinking |
| IC5 | Principal Security Engineer | 12+ years | Technical Vision, Innovation, Organizational Impact, Industry Expertise |

---

## IC2: Security Engineer

### Scope
Security implementation with guidance. Expected to implement security controls and conduct reviews.

### Competencies

#### Security Implementation

**Definition**: Implementing security controls and practices effectively

**Level 4 - Meets Expectations:**
- Implements security controls correctly
- Follows security standards and frameworks
- Writes secure code and configurations
- Documents security implementations
- Validates effectiveness of controls

**Level 3 - Needs Improvement:**
- Implementations work but have gaps
- Doesn't validate effectiveness
- Missing documentation

**Level 2/1 - Below Expectations:**
- Implementations create vulnerabilities
- Doesn't follow standards
- Cannot implement independently

**Development Suggestions:**
- Study security frameworks (NIST, CIS)
- Practice secure coding techniques
- Learn security testing tools
- Review security incidents

#### Threat Awareness

**Definition**: Understanding and identifying security threats

**Level 4 - Meets Expectations:**
- Understands common threat vectors
- Identifies vulnerabilities in systems
- Stays current on threat landscape
- Recognizes attack patterns
- Assesses risk appropriately

**Level 3 - Needs Improvement:**
- Basic awareness but misses nuances
- Doesn't stay current
- Over or underestimates risks

**Level 2/1 - Below Expectations:**
- Limited threat awareness
- Cannot identify vulnerabilities
- Poor risk assessment

#### Collaboration

**Definition**: Working effectively with development and operations teams

**Level 4 - Meets Expectations:**
- Partners with teams on security reviews
- Communicates risks and mitigations clearly
- Provides actionable recommendations
- Balances security with usability
- Builds security champions in teams

**Level 3 - Needs Improvement:**
- Limited engagement with teams
- Communication creates friction
- "No" without alternatives

**Level 2/1 - Below Expectations:**
- Creates adversarial relationships
- Blocks progress without guidance

## IC3: Senior Security Engineer

### Scope
Technical leadership within the security team. Expected to lead security projects and initiatives.

### Competencies

#### Security Implementation

**Definition**: Setting security implementation standards for the organization

**Level 4 - Meets Expectations:**
- Implementations serve as examples
- Establishes security standards and patterns
- Reviews implementations for quality
- Creates reusable security components
- Champions security culture

**Level 3 - Needs Improvement:**
- Good personal implementations but doesn't elevate team
- Doesn't create standards

**Level 2/1 - Below Expectations:**
- Quality regression
- Negative impact on security posture

#### Security Architecture

**Definition**: Designing secure systems and architectures

**Level 4 - Meets Expectations:**
- Designs security architecture for systems
- Applies defense in depth principles
- Balances security with performance/usability
- Documents security decisions
- Considers compliance requirements

**Level 3 - Needs Improvement:**
- Good designs but missing considerations
- Over-engineers security
- Doesn't document decisions

**Level 2/1 - Below Expectations:**
- Architectures have significant gaps
- Cannot design at this complexity

**Development Suggestions:**
- Study security architecture patterns
- Learn compliance frameworks
- Practice threat modeling
- Review security architectures

#### Threat Modeling

**Definition**: Systematically identifying and mitigating threats

**Level 4 - Meets Expectations:**
- Leads threat modeling sessions
- Uses structured methodologies (STRIDE, etc.)
- Identifies non-obvious threats
- Prioritizes risks effectively
- Creates actionable mitigations

**Level 3 - Needs Improvement:**
- Basic threat modeling but misses nuances
- Cannot lead sessions
- Mitigations not actionable

**Level 2/1 - Below Expectations:**
- Cannot perform threat modeling
- Misses significant threats

#### Mentoring

**Definition**: Developing junior security engineers

**Level 4 - Meets Expectations:**
- Actively mentors 1-2 security engineers
- Shares security knowledge and intuition
- Reviews work and provides feedback
- Helps mentees develop security judgment
- Creates learning opportunities

**Level 3 - Needs Improvement:**
- Answers questions but doesn't mentor
- Hoards knowledge

**Level 2/1 - Below Expectations:**
- Avoids mentoring
- Negative impact on mentees

## IC4: Staff Security Engineer

### Scope
Cross-team security impact. Expected to drive security strategy and architecture.

### Competencies

#### Technical Leadership

**Definition**: Leading security direction across organization

**Level 4 - Meets Expectations:**
- Sets security direction adopted org-wide
- Drives consensus on security decisions
- Unblocks teams on security challenges
- Builds credibility as security expert
- Balances security with business needs

**Level 3 - Needs Improvement:**
- Leads within team but not across org
- Direction not adopted

**Level 2/1 - Below Expectations:**
- Unable to lead at this scope
- Creates security silos

#### Security Architecture

**Definition**: Designing organization-wide security architecture

**Level 4 - Meets Expectations:**
- Designs security architecture for org
- Creates security patterns and standards
- Ensures compliance at scale
- Plans security roadmap
- Evaluates security tools and vendors

**Level 3 - Needs Improvement:**
- Good designs but limited adoption
- Doesn't consider org constraints

**Level 2/1 - Below Expectations:**
- Architecture has significant gaps
- Cannot operate at this scope

#### Cross-Team Collaboration

**Definition**: Working across teams on security initiatives

**Level 4 - Meets Expectations:**
- Builds relationships across org
- Facilitates security discussions
- Enables teams with security capabilities
- Leads incident response for major events
- Gathers feedback on security experience

**Level 3 - Needs Improvement:**
- Limited to familiar teams
- Doesn't build relationships

**Level 2/1 - Below Expectations:**
- Creates friction
- Adversarial approach

#### Strategic Thinking

**Definition**: Connecting security work to business objectives

**Level 4 - Meets Expectations:**
- Understands business risk context
- Proposes security initiatives aligned with business
- Thinks 1-2 years ahead on security
- Makes trade-offs with business context
- Quantifies security ROI

**Level 3 - Needs Improvement:**
- Security focus without business connection
- Short-term thinking

**Level 2/1 - Below Expectations:**
- Decisions misaligned with business

## IC5: Principal Security Engineer

### Scope
Organization-wide security strategy and influence.

### Competencies

#### Technical Vision

**Definition**: Defining long-term security direction

**Level 4 - Meets Expectations:**
- Creates compelling security vision
- Articulates multi-year security roadmap
- Aligns security strategy with company strategy
- Inspires others with security vision

**Level 3 - Needs Improvement:**
- Has vision but cannot drive adoption

**Level 2/1 - Below Expectations:**
- No clear security vision

#### Innovation

**Definition**: Driving security innovation

**Level 4 - Meets Expectations:**
- Evaluates emerging security technologies
- Leads proof-of-concepts
- Drives valuable innovations
- Creates security innovation culture

**Level 3 - Needs Improvement:**
- Innovates but doesn't spread

**Level 2/1 - Below Expectations:**
- No innovation

#### Organizational Impact

**Definition**: Improving security capabilities org-wide

**Level 4 - Meets Expectations:**
- Improves security posture org-wide
- Creates security tools for company
- Raises security bar for organization
- Develops other security leaders
- Influences hiring standards

**Level 3 - Needs Improvement:**
- Impact limited
- Doesn't develop others

**Level 2/1 - Below Expectations:**
- No organizational impact

#### Industry Expertise

**Definition**: Being a recognized security expert externally

**Level 4 - Meets Expectations:**
- Recognized security expert
- Speaks at security conferences
- Publishes security content
- Brings external perspectives
- Builds industry relationships

**Level 3 - Needs Improvement:**
- Expert internally only

**Level 2/1 - Below Expectations:**
- Not recognized as expert
